Every candidate below had its README read from source via `gh api`; for the top contenders I also read the schema/hook/tool source files cited inline. Smithery, mcp.so and PulseMCP produced no distinct hits beyond what Glama/GitHub already showed (coverage UNVERIFIED for those three). Nothing was installed or configured.

Scoring: `1` = yes, `0` = no, `P` = partial/opt-in. C6 is the hard requirement (content enters context only via an explicit tool call; never auto-injected).

## 2. Per-candidate notes

**1. agmsg (fujibee).** Not MCP at all: a skill plus per-host hooks plus ~40 bash scripts over one WAL-mode SQLite file (`~/.agents/skills/agmsg/db/messages.db`, `AGMSG_STORAGE_PATH` overridable), supporting Claude Code, Codex, Gemini CLI, Copilot CLI, Antigravity, OpenCode, Cursor, Grok Build and Hermes ([README](https://github.com/fujibee/agmsg), [llms.txt](https://github.com/fujibee/agmsg/blob/main/llms.txt)). Identity is `(team, agent-name)` registered per `(project, agent_type)`; `whoami.sh` reports `agent= teams= type= project=`, so family and git-resolved project are recorded but model is not ([whoami.sh](https://github.com/fujibee/agmsg/blob/main/scripts/whoami.sh)). Delivery modes are the crux for C6: default `monitor` streams messages into Claude via the Monitor tool, `turn` fires a Stop hook (`check-inbox.sh`) whose payload includes message bodies (`OUTPUT+="  [$ts] $from: $body"`), and only `mode off` is pure pull ([delivery modes](https://github.com/fujibee/agmsg#delivery-modes), [check-inbox.sh](https://github.com/fujibee/agmsg/blob/main/scripts/check-inbox.sh)). Presence is registration-based; `kill -0` liveness exists only to reclaim `actas` locks, and the PID-recycling hole is an open issue ([docs/actas.md](https://github.com/fujibee/agmsg/blob/main/docs/actas.md), [#67](https://github.com/fujibee/agmsg/issues/67)). Codex has no session-id story, so its receive side polls whichever identity `whoami.sh` picks first. To meet the spec you would add: model in the identity row, an online/offline roster derived from process liveness, and run it permanently in `mode off`.

**2. agent-bus (MustaphaSteph).** A stdio MCP server per session over one SQLite file (`~/.agent-bus/bus.db`), with plugin marketplaces for Claude Code, Codex, Kimi and Cursor and a curl installer for Gemini/OpenCode/others; no daemon, no auth ([README](https://github.com/MustaphaSteph/agent-bus)). The `agents` table holds name, capabilities, role, project (repo-derived), area, team, status, `session_id`, `last_seen`, `listening_until` — no family, model, pid or cwd ([db.ts](https://github.com/MustaphaSteph/agent-bus/blob/main/src/db.ts)); presence is `online|idle|stale|paused` computed from `last_seen` age, so a crashed process stays "online" until it ages out ([bus.ts](https://github.com/MustaphaSteph/agent-bus/blob/main/src/bus.ts)). `inbox` is a pull tool, but the shipped Claude Stop hook (`agent-bus poll-inbox`) returns `decision:"block"` with 500-char message previews in `reason`, i.e. content is auto-injected unless you skip the hook; the Codex client doc is pull-only ([poll-inbox.ts](https://github.com/MustaphaSteph/agent-bus/blob/main/src/cli/poll-inbox.ts), [docs/clients/codex.md](https://github.com/MustaphaSteph/agent-bus/blob/main/docs/clients/codex.md)). The human side is good (`agent-bus watch`, `team-chat`, `send`, `wait --notify`, a read-only cockpit). Scope has ballooned to ~50 tools with tasks, kanban, decisions and memories ([docs/tools.md](https://github.com/MustaphaSteph/agent-bus/blob/main/docs/tools.md)); 17 stars and no push since June.

**3. agent-bus-mcp (alessandrobologna).** The cleanest C6 story found: a stdio MCP server whose only messaging tool is `sync()` (read/write, optional long-poll), with server-side cursors keyed `(topic_id, agent_name)` in shared WAL SQLite, and `topic_join` returning a `reclaim_token` so a restarted peer can reclaim its name ([spec.md](https://github.com/alessandrobologna/agent-bus-mcp/blob/main/spec.md), [runtime reference](https://github.com/alessandrobologna/agent-bus-mcp/blob/main/docs/reference/runtime-reference.md)). Both `codex mcp add` and `claude mcp add` are documented. Presence is `topic_presence`, derived from `cursors.updated_at` — activity age, not liveness, and "presence expiry does not release the reservation". Scope is topics rather than repos, identity is a bare name, and the core is a Rust extension built with maturin plus an optional embeddings indexer, which is more build surface than the problem needs. Adding family/model/cwd fields and a liveness check would be small; retrofitting repo scoping is a data-model change.

**4. mcp_agent_mail (Dicklesworthstone).** The dominant project in this space: identities, inbox/outbox, threads, acks, advisory file leases, a Git markdown archive per project plus SQLite FTS, and an auto-installer that wires Claude Code, Codex, Gemini CLI and Factory Droid ([README](https://github.com/Dicklesworthstone/mcp_agent_mail)). It is the only candidate whose identity record already matches C3: `register_agent(project_key, program, model, name?)` with `project_key` = repo absolute path and `last_active_ts` on the agents table. Delivery is pull (`fetch_inbox`, `resource://inbox/...`); presence is `last_active_ts` plus `sweep_stale_agents(threshold_seconds)`, activity-based. Footprint is the deal-breaker: a Streamable-HTTP daemon on :8765 with a bearer token (a `serve-stdio` mode exists but is secondary), Python 3.14, ~33 runtime deps including fastapi, sqlalchemy, redis, litellm, pillow, GitPython and tiktoken, and an installer that also installs Beads ([pyproject.toml](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/main/pyproject.toml)). The [LICENSE](https://github.com/Dicklesworthstone/mcp_agent_mail/blob/main/LICENSE) is MIT with a rider revoking all rights for OpenAI, Anthropic, their affiliates and anyone "acting on behalf of" them, including contractors — worth a legal read before adopting. A Rust port exists ([mcp_agent_mail_rust](https://github.com/Dicklesworthstone/mcp_agent_mail_rust), 160★, "34 tools, Git-backed archive, TUI"), not inspected in depth.

**5. AMQ (avivsinai).** A single Go binary implementing Maildir (tmp→new→cur, fsync, no-replace publish) with JSON-frontmatter + Markdown messages, threads, kinds, priorities, receipts and a DLQ; `amq setup` detects Claude, Codex, Grok and Cursor and writes `.amqrc`/`.amq/launch.json` into the repo ([README](https://github.com/avivsinai/agent-message-queue)). This is the best human-readability story here (`cat`, `grep`, `git`). Identity is `AM_ME` plus opaque `AM_ROOT_ID`/`AM_SESSION` tokens; family/model are not documented as recorded (UNVERIFIED). Presence is explicitly *advisory* (`presence set`/`presence list`), and `amq doctor --ops` reports "presence freshness" — not liveness. `amq list --new` / `amq drain` are pure pull, but the co-op flow relies on `amq wake`, which by default uses TIOCSTI to type a fixed "doorbell" into the agent's terminal — a fake keystroke that becomes a user turn ([COOP.md](https://github.com/avivsinai/agent-message-queue/blob/main/COOP.md), [wake-doorbell-acknowledgement.md](https://github.com/avivsinai/agent-message-queue/blob/main/docs/wake-doorbell-acknowledgement.md)); `--inject-mode none` disables it. The wake subsystem (lock generations, repair floors, keepalive supervisor, bridge courier) is far larger than the messaging core.

**6. cross-agent-teams-mcp / xats (jtianling).** A persistent daemon on `127.0.0.1:9100` (Streamable HTTP MCP + SQLite at `~/.cross-agent-teams-mcp/data.db`) with `register_agent` (auto-detected agent type, role, team), 1:1 messages, team/role broadcast, and per-agent wake: Claude via a stdio channel proxy launched with `--dangerously-load-development-channels`, Codex via its app-server WebSocket, opencode via HTTP, others via tmux paste ([README](https://github.com/jtianling/cross-agent-teams-mcp)). The README states the C6-compliant configuration explicitly ("minimum config: mailbox only, no push wake … you have to call `get_inbox` yourself"), but everything else in the project pushes toward wake. Requires a daemon; per-project scoping and a human CLI were not evident (UNVERIFIED). Also grew cross-device hub support, which is beyond the spec.

**7. claude-peers-mcp (louislva).** The most-starred single-vendor answer: a broker daemon on `localhost:7899` + SQLite, each Claude session's stdio MCP server polls every second, and inbound messages are pushed into the session via the channels protocol ([README](https://github.com/louislva/claude-peers-mcp)). `list_peers` carries cwd, git repo and a summary, scoped to machine/directory/repo, and the broker "cleans up dead peers" (heartbeat-based). It fails C2 (Claude only, requires claude.ai login for channels) and C6 (push by design), requires Bun, and has had no commits since April. Optional `OPENAI_API_KEY` for auto-summaries.

**8. claude-presence (garniergeorges).** Small stdio MCP server (SQLite at `~/.claude-presence/state.db`, ~2700 LOC, Node 18, zero daemon) with a session registry (project, branch, cwd, intent, `client_session_id`), named resource locks, and a broadcast/DM inbox ([README](https://github.com/garniergeorges/claude-presence)). It is technically loadable from Codex, but slash commands, hook identity resolution (`CLAUDE_SESSION_ID`) and docs are Claude-only. `read_inbox` is pull; the optional `UserPromptSubmit` hook injects the full unread inbox as `additionalContext`, so leave it uninstalled for C6. Presence is a heartbeat with a 24-hour TTL — fails open for a day after a crash. Its own comparison table is a useful map of the niche.

**9. claude-codex-mcp-bridge (WebisityStudio).** Purpose-built for exactly the Claude Code + Codex pair: one stdio MCP server per client over a shared SQLite WAL file, with `bridge_send/inbox/ack/thread`, broadcasts, idempotency keys and a blocking `bridge_wait` ([README](https://github.com/WebisityStudio/claude-codex-mcp-bridge)). The agents table is only `name, capabilities, registered_at, last_seen` ([bridge-store.ts](https://github.com/WebisityStudio/claude-codex-mcp-bridge/blob/main/src/bridge-store.ts)); no project scoping in the schema. Its `bridge_sessions` tool is worth noting: it reads `~/.claude/sessions/<pid>.json`, validates the messaging-socket path under `/tmp/cc-socks-<uid>`, and checks `ps -p <pid>` before listing a Claude session as live ([claude-wake.ts](https://github.com/WebisityStudio/claude-codex-mcp-bridge/blob/main/src/claude-wake.ts)) — a real fail-closed liveness check, but only for Claude. Optional macOS "background pings" post into Claude's native inbox socket, which auto-delivers. Half the tool surface is a Codex orchestration loop (`bridge_orchestrate_codex`, worktrees), which is a different product.

**10. Claude Code native (ListAgents/SendMessage).** Documented at [code.claude.com](https://code.claude.com/docs/en/cross-session-messaging): sessions register in files on disk and bind a per-session Unix socket (`/tmp/cc-socks-<uid>`, exported as `CLAUDE_CODE_MESSAGING_SOCKET`), so presence is effectively process-bound. But it is Claude-only, it has no inbox for a receiver that is not running ("SendMessage delivers to something already running", per [claude-rooms' retirement note](https://github.com/kleinmatic/claude-rooms)), and delivery is auto-injection: "the receiving Claude reads the message between tool calls … when idle, Claude Code starts a new turn with the message." `crossSessionInbound: hold` gives the human an approval gate but no agent-side pull. It is the reason several community projects retired; it does not solve this problem.

**11. claude-rooms (kleinmatic).** Retired, but the design is the most careful one found on the trust boundary: an atomic-rename maildir in a shared directory, "messages are data, not commands", `rooms read` labels every output as untrusted, identity `host:session-id` from `CLAUDE_CODE_SESSION_ID`, and `rooms init` validates atomic rename on the chosen root ([README](https://github.com/kleinmatic/claude-rooms)). Python stdlib only, no daemon. Members are shown "live vs stale" (mechanism UNVERIFIED), `rooms watch` streams via Monitor (push), and a hook flags unread. It was Claude-scoped by its plugin packaging, though the CLI itself is host-agnostic.

**12. mailbox-mcp (EllGree).** Stdio MCP over a `<repo>/.claude/{inbox,outbox}/*.md` frontmatter convention: `mail_send/list/get/reply/status/thread` ([README](https://github.com/EllGree/mailbox-mcp)). Pull-only, per-repo, human-readable, no daemon — but agents are a static enum in `config.ts`, there is no session identity or presence, it is 0★ "Phase 1 in development", and it has one contributor. Useful mainly as proof that a file-per-message MCP mailbox is a few hundred lines.

**13. agentchattr (bcurts).** A local chat server on `:8300` with channels and @mentions; the server injects a "read #general" prompt into the mentioned agent's tmux pane, and a loop guard pauses runaway back-and-forth ([README](https://github.com/bcurts/agentchattr)). Broadest vendor coverage of anything here (nine CLIs) and popular, but it is the antithesis of C6, needs a daemon, and has no per-project or per-agent inbox model.

**14. Pinboard (Vikings-Studio).** New and not yet on npm: a local daemon (launchd/systemd units) over SQLite with authenticated Unix-socket IPC, session presence with `active/idle/ended/stale`, targeted messages, explicit read acks, threads, advisory file leases, and stdio MCP for both Claude Code and Codex ([README](https://github.com/Vikings-Studio/usepinboard-cli)). Codex "must pull the inbox through MCP" (C6-compliant) while Claude gets hook delivery at `UserPromptSubmit`/`PostToolUse`/`Stop`. Optional WorkOS "Teams" cloud relay. Requires Node 24 and the release-candidate `node:sqlite`. Too early and too daemon-shaped, but the presence state machine is a good reference.

**15. AgentConduit (aididhaiqal).** Six days old, 0★. Its motivating incident is precisely the target scenario ("Claude and Codex were working in separate Git worktrees … both tried to merge"), and its workspace identity (repo, worktree, branch, HEAD, dirtiness) is the richest C3 record found ([README](https://github.com/aididhaiqal/AgentConduit)). Presence is "online, stale, offline; presence is liveness, never proof of completion". It runs as a loopback broker daemon with a private SQLite, adds jobs, checkpoints and FIFO integration leases per target ref, and has an optional multi-PC hub. Watch it; do not depend on it yet.

**16. agentwisper (jhqian).** A single-process Streamable-HTTP broker on `:8000` with SQLite, 26 tools, P2P/RPC/pub-sub, squads, offline buffering and reconnect; documented for both Claude Code and Codex ([README](https://github.com/jhqian/agentwisper)). Pull/wait tools only (C6 ok), but it is a daemon, has no repo scoping, no human CLI, and 0★.

**17. h5i msg (Koukyosyumei).** A git-native design: messages are JSON lines in `refs/h5i/msg`, identity is `$H5I_AGENT` injected per host (`claude` in Claude Code), typed verbs `send/ask/review/risk/handoff/reply/ack/done/decline`, `all` broadcast, and `h5i share push/pull` to move the ref ([protocol doc in h5i-db](https://github.com/Koukyosyumei/h5i-db/blob/main/.claude/h5i.md)). A Stop hook "surfaces new messages between turns" (push). The Medium write-up returned 403, the `h5i-dev/h5i` repo is an unrelated Rust browser, and no `h5i` package exists on crates.io, npm or PyPI, so the CLI itself is UNVERIFIED as obtainable.

**18. slm-mesh (qualixar).** Auto-started localhost broker with bearer auth, Unix-socket push (<100 ms), peer discovery scoped by machine/dir/git repo, heartbeat crash detection, file locks, shared state; any MCP client ([README](https://github.com/qualixar/slm-mesh)). Push delivery fails C6, the license is Elastic-2.0 (source-available, not open source), and the last push was May.

**19. claude-mailbox (zach-source).** Identity detection is good (`identity.py`: session id + git project/branch/worktree; background heartbeat + atexit deregister; leader election) and the transport is stdio ([README](https://github.com/zach-source/claude-mailbox)), but it is a thin wrapper over Beads' `bd --global` on a shared Dolt server (~69 Python deps) and delivers via Claude channel push.

**20. postal-mcp (tkellogg).** Two tools, `send_message` and a blocking `check_mailbox`, over SQLite behind an HTTP-only MCP server ([README](https://github.com/tkellogg/postal-mcp)). Historically interesting (Claude ↔ Gemini in mid-2025), dead since.

## 3. Verdict: closest existing thing

**Closest:** [fujibee/agmsg](https://github.com/fujibee/agmsg) in `mode off`. It is the only actively maintained, popular project that is simultaneously local-only, genuinely cross-vendor today (Claude Code and Codex both first-class), daemon-free, per-project-registered, human-inspectable (sqlite3 + community TUI/viewer), and has a configuration where message content enters context only when the agent runs `/agmsg`. Runner-up for a pure-MCP shape is [alessandrobologna/agent-bus-mcp](https://github.com/alessandrobologna/agent-bus-mcp), whose `sync()`-only surface is the cleanest C6 design found.

**Does adopting/forking beat a ~2-file stdlib tool? No, for this spec.** Three reasons, each grounded above:

1. **C6 runs against the grain of every project.** agmsg, agent-bus, AMQ, xats, Pinboard, claude-presence and the bridge all invest their effort in *wake* — Monitor streams, Stop-hook `decision:block`, TIOCSTI doorbells, channel proxies. Pull-only is a de-configured corner of each, not a maintained mode. A fork would spend its life fighting upstream defaults.
2. **Fail-closed presence (C4) exists nowhere for the roster.** Every candidate uses `last_seen`/heartbeat/TTL (24 h in claude-presence; "stale" thresholds in agent-bus and agent-bus-mcp). The only process-bound checks are Claude-specific (native socket; the bridge's `ps -p` over `~/.claude/sessions/*.json`) or lock-specific (agmsg's `kill -0` with an open PID-recycling issue). You would build C4 from scratch regardless.
3. **The one project with the right identity record (C3) — mcp_agent_mail — has the wrong footprint** (HTTP daemon, ~33 deps, Python 3.14, and a license rider that excludes anyone working for or with Anthropic/OpenAI).

The two-file tool is justified: one stdio MCP server (so both Claude Code and Codex load it with `claude mcp add` / `codex mcp add`) and one CLI, both stdlib, sharing one store. The design work is choosing which mechanisms to lift.

## 4. Design ideas worth stealing

**Presence that fails closed (the gap nobody fills).** A stdio MCP server is spawned by the agent process, so `os.getppid()` at registration *is* the agent. Record `(ppid, process_start_time)` and define online as "ppid alive AND start time unchanged". This is agmsg's `kill -0` reclaim ([actas.md](https://github.com/fujibee/agmsg/blob/main/docs/actas.md)) with the PID-recycling hole ([#67](https://github.com/fujibee/agmsg/issues/67)) closed the way AMQ's wake lock does it — its owner record stores both `pid` and `process_start` ([wake-lifecycle.md](https://github.com/avivsinai/agent-message-queue/blob/main/docs/wake-lifecycle.md)). Cross-check against Claude's own registry when present, as the bridge does (`~/.claude/sessions/<pid>.json` + socket path under `/tmp/cc-socks-<uid>`, [claude-wake.ts](https://github.com/WebisityStudio/claude-codex-mcp-bridge/blob/main/src/claude-wake.ts)). Also expose agent-bus's three-state `online | idle | stale` with a `listening_until` stamp so "alive but not reading" is distinguishable ([bus.ts](https://github.com/MustaphaSteph/agent-bus/blob/main/src/bus.ts)).

**Identity.** Use mcp_agent_mail's triple `(program, model, project_key=abs repo root)` ([README §register_agent](https://github.com/Dicklesworthstone/mcp_agent_mail)); detect the family from the parent process/env the way agmsg's `lib/detect-cli-type.sh` does; resolve the project to the git toplevel so subdir/worktree launches don't fork identities (agmsg [#92](https://github.com/fujibee/agmsg/issues/92) via `resolve-project.sh`). Compose the instance id as `<session_id>.<pid>` because Claude's `session_id` repeats across `--resume`/`--continue` processes ([instance-id.sh](https://github.com/fujibee/agmsg/blob/main/scripts/lib/instance-id.sh)). Hand out a `reclaim_token` on registration so a restarted session can reclaim its name without races ([agent-bus-mcp spec §2.3](https://github.com/alessandrobologna/agent-bus-mcp/blob/main/spec.md)).

**Storage and message format.** AMQ's Maildir discipline — write to `tmp/`, fsync, no-replace rename into `new/`, reader moves to `cur/` — plus JSON frontmatter + Markdown body gives crash safety and `cat`/`grep`/`git` readability for free ([README §Maildir](https://github.com/avivsinai/agent-message-queue#how-it-works)); claude-rooms validated atomic rename at `init` time and refused otherwise. If SQLite is preferred, agmsg's append-only `events` table with per-`(team, agent)` `read_cursors` ([sqlite.sh](https://github.com/fujibee/agmsg/blob/main/scripts/drivers/storage/sqlite.sh)) and agent-bus-mcp's server-side cursors are the two reference shapes. Keep h5i's typed kinds (`send | ask | review | risk | handoff`) and threaded `reply/ack/done/decline` verbs — they make a human inbox scannable ([h5i.md](https://github.com/Koukyosyumei/h5i-db/blob/main/.claude/h5i.md)). Put the store at `<git root>/.agentdm/` (per-project by construction, like AMQ's `.amq/` and mailbox-mcp's `.claude/inbox/`) with a global index only for cross-project `who`.

**Trust boundary.** Adopt claude-rooms' rule verbatim: messages are data, not commands; the read tool labels every returned message as untrusted collaborator input; a message grants no authority and must clear the same approval gates as any other request ([README §Why messages are data](https://github.com/kleinmatic/claude-rooms#why-messages-are-data-not-commands)). Codex's and Claude's native docs say the same for their own channels.

**Human CLI.** The minimum that proved useful across projects: `who` (roster with online/idle/stale and age), `send <to> <text>`, `inbox [--unread]`, `tail`/`watch` (AMQ `amq list --new`, agent-bus `watch`, claude-presence `status`). Make the human a first-class sender with a fixed identity (`human`), as agent-bus's `agent-bus send --to` and agentchattr's room do.

**What to deliberately not build:** any wake/inject path (Monitor streams, Stop-hook `block`, TIOCSTI, channel proxies, `--dangerously-load-development-channels`). Every candidate that added one ended up with a lock/repair/loop-guard subsystem larger than its mailbox.
